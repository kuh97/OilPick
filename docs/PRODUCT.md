## 1. Product Overview

### 1.1 한 줄 정의

출발지와 목적지를 입력하면 그 경로에서 주유하기 가장 좋은 주유소를 찾아주는 서비스.
**단, 경로 위에 없으면 "없습니다"로 끝내지 않고, 우회할 가치가 있는 주유소까지 찾아 경로를 만들어준다.**

### 1.2 해결하려는 문제

기존 서비스(티맵·네이버지도·카카오내비·오일나우)는 전부 **반경 하드 필터**를 씁니다.

```
경로 확정 → 반경 N km 안에서 검색 → 조건에 맞는 게 없음 → "검색 결과 없음"
                                                        ↑
                                            사용자의 탐색이 여기서 끝난다
```

반경 밖 주유소는 **존재 자체가 사용자에게 전달되지 않습니다.** 사용자는 "조금만 돌아가면 되는 곳이 있을 텐데"를 확인할 방법이 없습니다.

### 1.3 핵심 가치

> **반경으로 자르지 않는다. 우회 비용과 이득을 비교해서 순위를 매긴다.**

이 제품의 차별점은 두 줄뿐입니다.

1. 반경 밖까지 탐색한다
2. 우회 비용과 이득을 계산해서 순위를 매긴다

나머지 기능은 전부 이 둘을 성립시키기 위한 부속입니다.

### 1.4 이 차이가 드러나는 상황

정직하게: **휘발유·경유로 짧은 경로를 검색하면 기존 서비스와 차이가 거의 없습니다.** 전국에 주유소가 1만 개 이상이라 경로 주변에 항상 있기 때문입니다.

차이가 드러나는 상황은 셋입니다.

| 상황                                         | 왜 발생하는가                              |
| -------------------------------------------- | ------------------------------------------ |
| **LPG 차량**                                 | 자동차충전소는 주유소보다 훨씬 희소함      |
| **조건 조합** (예: LPG + 세차)               | 두 조건을 모두 만족하는 곳은 급격히 줄어듦 |
| **저밀도 구간** (강원 산간, 고속도로 장구간) | 지역 자체에 시설이 적음                    |

→ 제품 메시지와 초기 사용자 확보를 **LPG·장거리**에 맞춥니다.

### 1.5 타깃 사용자

| 우선순위 | 세그먼트                            | 필요한 이유                                  |
| -------- | ----------------------------------- | -------------------------------------------- |
| **1**    | LPG 차량 장거리 운전자              | 충전소 밀도가 낮아 "경로에 없음"이 자주 발생 |
| 2        | 조건이 있는 운전자 (주유 + 세차 등) | 조건 조합 시 후보가 급감                     |
| 3        | 주말 장거리 레저 운전자             | 우회 비용 판단 니즈. 후보 부족은 잘 안 생김  |
| 4        | 영업·출장 운전자                    | 주행거리가 커서 절감액 절대치가 큼           |

**타깃하지 않음**

- 일상 근거리 주행자 — 단골 주유소가 있고 경로 최적화 여지가 없음
- 전기차 운전자 — 체류 시간·판단 변수·데이터 신선도 요구가 전부 다름. **별도 제품** (§2.3)

### 1.6 설계 원칙 5가지

개발 중 판단이 갈릴 때 이 순서로 결정합니다.

1. **계산은 전부 결정론적으로.** 금액·거리·시간에 AI를 쓰지 않습니다.
2. **추정치와 실측치를 구분해서 표시한다.** 직선거리 기반 추정은 `약 4.2km`처럼 "약"을 붙이고, 실제 경유 경로로 계산한 값만 확정 수치로 씁니다.
3. **모르는 값은 묻지 않고 기본값을 쓰되, 기본값을 화면에 밝힌다.** 연비를 물으면 이탈합니다.
4. **탐색을 넓혔으면 넓혔다고 말한다.** 이 고지가 곧 제품의 정체성입니다.
5. **빈 화면으로 끝내지 않는다.** 반드시 대안(조건 완화·목적지 근처 검색)을 제시합니다.

### 2.3 향후 확장 (범위 밖, 명시만)

- **차종·연료·연비·하이패스 등 세부 차량 정보 입력** — 지금은 승용차 기준 기본값만 사용(§9.2). 개인화하려면 로그인으로 저장해야 하는데, 로그인 자체가 MVP에서 제외된 상태(§2.2)라 로그인 인프라가 생긴 뒤 별도 Phase로 진행
- **다구간 주유 최적화** — 장거리에서 여러 번 주유할 때 "어디서 얼마씩". 연료 잔량 입력 정확도 문제로 난이도 높음
- 사용자 가격·폐업 제보
- 주행 중 실시간 추천 (앱 전용)
- 전기차 충전소 — **별도 제품.** 아래 이유로 이 제품에 합치지 않습니다

| 축                 | 내연기관 | 전기차                      |
| ------------------ | -------- | --------------------------- |
| 체류 시간          | 5분      | 급속 30~60분                |
| 판단 변수          | **가격** | **충전기 가용성·규격·출력** |
| 데이터 신선도 요구 | 하루 6회 | **분 단위 실시간**          |
| 실패의 대가        | 불편     | 주행 불가                   |

"+18분 우회"와 "충전 45분"이 섞이면 §8의 목적함수가 성립하지 않습니다.
다만 DB 스키마는 일반 개념(`refuel_point` / `energy_type`)으로 두어 향후 마이그레이션을 피합니다 ([`ARCHITECTURE.md`](ARCHITECTURE.md) §7).

## 3. 핵심 용어

개발 전체에서 이 용어를 그대로 씁니다. **단위는 미터(m) · 초(s) · 원(₩)입니다** ([`../AGENTS.md`](../AGENTS.md) §7.4).

| 용어             | 기호                | 정의                                                    |
| ---------------- | ------------------- | ------------------------------------------------------- |
| 기본 경로        | `R₀`                | 출발지 → 목적지 직행 경로 (주유소 경유 없음)            |
| 기본 거리 / 시간 | `D_base` / `T_base` | `R₀`의 총 거리(m) / 총 소요시간(초)                     |
| 경유 경로        | `R_s`               | 출발지 → 주유소 s → 목적지 경로                         |
| **우회 거리**    | `ΔD(s)`             | `R_s.distance − D_base` (m, 음수면 0)                   |
| **우회 시간**    | `ΔT(s)`             | `R_s.duration − T_base` (초, 음수면 0)                  |
| 수직 거리        | `d_perp(s)`         | 주유소 s에서 기본 경로 폴리라인까지의 최단 직선거리 (m) |
| 탐색 티어        | `T1/T2/T3`          | 주유소가 경로에서 얼마나 떨어져 있는지의 등급 (§6.4)    |
| 기준가           | `P_ref`             | "그냥 아무 데나 들렀을 때 낼 법한 가격" (§6.3)          |
| **순절감액**     | `NetSaving(s)`      | 기준가 대비 절약분에서 우회 연료비를 뺀 금액 (§6.5)     |
| 여정 총비용      | `TotalCost(s)`      | 주유비 + 우회 연료비                                    |
| 기준 모드        | —                   | 최단거리 / 최소비용 / 균형 (§8)                         |

## 4. User Flow

### 4.1 화면 구조

```
[홈 / 경로 입력]
      │
      ├──▶ [결과 목록] ──▶ [주유소 상세] ──▶ 외부 내비 앱
      │         │
      │         └──▶ [필터 시트]
      │
      └──▶ [내 주변 주유소] ──▶ 외부 내비 앱
```

라우팅: `/`, `/result`, `/station/:id`, `/nearby`. 필터는 모달.

### 4.2 핵심 시나리오 — LPG 장거리

```
1. 홈에서 "성남" → "춘천" 입력, 연료 LPG 선택
2. [찾기] 탭
3. 로딩: 경로 찾는 중 → 주유소 찾는 중 → 범위를 넓히는 중 (15km) → 우회 경로 계산 중
4. 결과: "경로 주변 3km에 조건에 맞는 충전소가 1곳뿐이어서 7km까지 넓혀 찾았습니다"
5. 1위 카드: 🟡 우회 · E1 홍천충전소 · 1,102원/L · +18분 · +12.4km · 💡 3,252원 이득
6. 카드 탭 → 상세에서 기본 경로(회색)와 경유 경로(강조)를 지도로 비교, 추천 이유 확인
7. [카카오맵] 탭 → 주유소가 경유지로 들어간 경로가 카카오맵에서 열림
```

**4단계의 고지 배너가 이 제품의 존재 이유입니다.** 기존 서비스가 "검색 결과 없음"으로 끝냈을 순간입니다.

> 3단계의 `15km`는 **탐색 상한**(`T3_MAX`)이고, 4단계의 `7km`는 **실제로 채택된 후보의 최대 거리**입니다. 둘은 다른 값이며 섞어 쓰면 안 됩니다 (§5.3 ②, §10.3).

### 4.3 보조 시나리오

| 시나리오        | 흐름                                                      |
| --------------- | ------------------------------------------------------- |
| 경로상에 후보 충분 | 우회 배너 없이 T1·T2 위주 결과. 기존 서비스와 유사한 경험 |
| 필터로 0건      | 어떤 필터가 원인인지 특정 → 해제 버튼 제시                |
| 전 구간 0건     | 목적지 근처 / 출발지 근처 주유소 보기 제시                |
| 경로 없이 주유  | 홈에서 [내 주변 주유소] → 가격순/거리순                   |

## 5. Feature Specification

### 5.1 F1 — 경로 입력

**목적** 출발지·목적지를 좌표로 확정한다.

**입력**

| 항목      | 필수 | 방식                                              |
| --------- | ---- | ------------------------------------------------- |
| 출발지    | ✅   | 장소 검색 자동완성 / "현재 위치" 버튼             |
| 목적지    | ✅   | 장소 검색 자동완성                                |
| 연료 종류 | ✅   | 3택 (휘발유 / 경유 / LPG). 기본값은 마지막 선택값 |
| 고속도로·자동차전용도로 회피 | ➖ | 체크박스(스위치). 기본값 OFF, `localStorage` 저장 |

**처리 규칙**

- 검색어 `PLACE_QUERY_MIN_LEN`(2자) 이상부터 자동완성 호출, `PLACE_DEBOUNCE_MS`(300ms) 디바운스
- 자동완성 결과 최대 5건. `장소명 + 주소` 2줄 표시
- "현재 위치"는 브라우저 Geolocation. 권한 거부 시 **조용히 무시**하고 텍스트 입력으로 유도
- 출발지와 목적지 사이가 `MIN_OD_GAP`(500m) 이내면 오류 안내
- 최근 검색 3건을 `localStorage`에 저장하고 홈에 노출

**고속도로·자동차전용도로 회피 (Phase 12 추가)**

카카오 길찾기 API의 `avoid=motorway` 그대로다. §5.2의 시설·브랜드 필터나 §5.3 ⑥
최대 우회 시간 필터와 달리 **후보를 거르는 게 아니라 `baseRoute` 자체를 바꾸는 검색
조건**이다 — 체크 상태가 바뀌면 카카오 길찾기부터 다시 호출해야 한다(경로 폴리라인이
통째로 달라지므로 bbox 재계산 → 후보 재수집 → 정밀 재측정까지 파이프라인 전체가
다시 돈다). 그래서 클라이언트에서는 `filters`와 같은 "바뀌면 재검색" 부류로 다루고
(`vehicle`·`maxDetourMinutes`처럼 즉시 재계산하는 부류가 아님), 서버에서는 캐시 키에
반드시 포함한다 — 빠뜨리면 회피를 켠 사용자가 끈 사용자의(또는 그 반대) 캐시된 경로를
그대로 받는다 (`infra/cache/keys.routeKey`).

**체크 해제(기본값)가 "모든 경우를 다 검색한다"는 뜻은 아니다.** 카카오 API는 호출 1번에
경로 1개만 준다 — 체크 해제 시엔 그냥 `avoid` 파라미터를 안 보내 카카오의 `priority:
RECOMMEND`가 알아서 판단하게 둘 뿐이고, 그 판단은 통행료가 있는 구간을 자유롭게 포함할
수 있다. "회피 안 함"과 "두 경로를 비교해서 보여줌"은 다른 기능이며, 후자는 후보마다
카카오 호출이 2배로 늘어 지금은 구현하지 않는다.

**출력**

```
{ origin: {lat, lng, name}, destination: {lat, lng, name}, fuel: "GASOLINE"|"DIESEL"|"LPG", avoidHighway: boolean }
```

**예외**

| 상황                      | 처리                                                   |
| ------------------------- | ------------------------------------------------------ |
| 자동완성 API 실패         | "장소를 찾을 수 없습니다" + 재시도                     |
| Geolocation 거부/타임아웃 | 버튼 비활성 후 텍스트 입력 유도. 에러 모달 띄우지 않음 |
| 출발지 ≈ 목적지           | 검색 버튼 비활성 + 안내 문구                           |

### 5.2 F2·F6 — 필터

**목적** 후보 주유소를 사용자 조건으로 좁힌다.

**필터 항목** (오피넷이 제공하는 것만)

**처리 규칙**

  - 예: _"세차장 조건 때문에 후보가 없습니다. [세차 조건 해제하고 다시 찾기]"_

**② 우회 고지 배너 — 제거 금지**

회랑 쿼리는 경로 폴리라인 bbox 안의 후보를 T3_MAX(15km)까지 한 번에 가져옵니다. 그중
`T2_MAX(3km) < d_perp ≤ T3_MAX` 이면서 `NetSaving > 0`인 T3 후보가 최종 목록에 남으면,
"경로 밖까지 살펴서 돌아가도 이득인 곳을 담았다"를 배너로 알립니다. 이 문장이 뜨는
순간이 이 제품의 존재 이유입니다.

| 조건                       | 문구                                                                                |
| -------------------------- | --------------------------------------------------------------------------------- |
| 최종 목록에 T3 존재 (`expansion.triggered`) | `경로에서 {실제확장거리} 떨어진 곳까지 살펴, 돌아가도 이득인 곳을 함께 담았습니다.` |
| T3 없음                    | **배너 없음**                                                                     |

| 변수             | 값                                                                            |
| ---------------- | --------------------------------------------------------------------------- |
| `{실제확장거리}` | 최종 목록에 남은 T3(geoTier)의 최대 `d_perp`를 km로 올림 (§7.2 STEP 11 7번) |

- **고정값 `15km`를 쓰지 마십시오.** `T3_MAX`는 탐색 상한이지 실제로 찾은 거리가 아닙니다.
  7km까지만 찾았는데 "15km까지 넓혀 찾았습니다"라고 하면 거짓입니다
- 배너는 **`result` 이벤트를 받은 뒤 확정 렌더링**합니다. `partial` 시점의 `finalRadiusM`은
  아직 후보가 걸러지기 전이라 달라질 수 있습니다

**③ 기준 모드 탭**

- 3개: `균형`(기본) / `최소비용` / `최단거리`
- 탭 전환 시 순위 재계산 (§8)
- **API 재호출 없이 즉시 반영되어야 함.** 이미 받아온 후보를 재정렬하는 것

**④ 결과 카드**

| 요소              | 표시 규칙                                                                                                                                                   |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 순위 번호         | 현재 모드 기준 순위                                                                                                                                         |

| ---------------- | ---------------- |
| `MEDIAN_T1T2`    | `경로 주변 평균` |
| `SIGUNGU_AVG`    | `지역 평균`      |

- **연비는 선택된 연료의 기본값을 씁니다** (§9.2). LPG 검색인데 휘발유 연비를 표시하면 안 됩니다
- 탭하면 시트가 열려 연비·주유량·시간가치 수정 가능. **수정 시 API 재호출 없이 즉시 재계산**
- 수정값은 `localStorage` 저장

**⑥ 최대 우회 시간 필터 (Phase 11 추가)**

같은 "계산 전제 수정" 시트 안에 넣지만 성격이 다릅니다 — **금액 계산에 영향을 주지 않는
표시 필터**입니다. 이보다 우회 시간이 긴 후보를 숨기기만 합니다.

- 기본값 `DEFAULT_MAX_DETOUR_MINUTES`(20분, `params.ts`). 사용자가 수정 가능, `localStorage` 저장
- §5.2의 시설·브랜드 등 필터와 달리 **바뀌어도 재검색하지 않습니다** — 이미 받은 후보
  목록(전부 실측 완료, §7.3)을 클라이언트에서 다시 거르기만 합니다 (③·⑤와 같은 부류)
- 서버의 `SHORT_ROUTE_DETOUR_TIME_CAP_S`(20분, §9.1·§10.1 A6)와 기본값이 같지만 역할이
  다릅니다 — 그건 "이 이상은 같은 여정이 아니다"라는 기술적 하한(조정 불가)이고, 이건
  "나는 이 이상은 안 돌아간다"는 사용자 취향(조정 가능)입니다. **이 필터를 서버 하한보다
  느슨하게 풀어도 서버가 이미 뺀 후보는 되살아나지 않습니다** — 표시 범위를 더 좁힐 수만
  있다는 뜻입니다
- 이 설정 때문에 0건이 되면(필터 때문이 아니라) §5.3 "후보 0건일 때"의 전용 문구·버튼을 씁니다

**후보 0건일 때 — 빈 화면 금지**

```
┌──────────────────────────────────────────────┐
│  이 경로에서 조건에 맞는 주유소를 찾지 못했습니다 │
│  ({실제탐색거리}까지 탐색)                     │
│                                              │
│  [ 세차 조건 해제하고 다시 찾기 ]              │  ← 필터가 원인일 때만
│  [ 최대 우회 시간을 {N}분으로 늘리기 ]         │  ← ⑥ 필터가 원인일 때만
│  [ 목적지 근처 주유소 보기 ]                   │
│  [ 출발지 근처 주유소 보기 ]                   │
└──────────────────────────────────────────────┘
```

`{N}`은 남은 후보 중 가장 짧은 우회 시간(분, 올림) — "얼마나 늘려야 하나"를 사용자가
직접 가늠하게 하지 않고 정확한 값을 줍니다.

`{실제탐색거리}`는 상황에 따라 다릅니다. **여기도 `15km`를 하드코딩하지 마십시오.**

회랑 쿼리는 언제나 `T3_MAX`(15km)까지 훑으므로 전 구간 0건일 때 `{실제탐색거리}`는
`T3_MAX`입니다. **그래도 `params.T3_MAX`를 참조하고 하드코딩하지 마십시오.**

│  ⚠️ 가격은 실제와 다를 수 있습니다.            │
│     먼 거리를 우회하므로 전화 확인을 권합니다.  │
├──────────────────────────────────────────────┤
│  [ 카카오맵 ]  [ 네이버지도 ]  [ 티맵 ]        │
└──────────────────────────────────────────────┘
```

**추천 이유 생성 규칙 — AI를 쓰지 않습니다**

템플릿 규칙으로 생성합니다. 아래 조건을 위에서부터 검사해 **처음 맞는 것 하나**를 씁니다.

| #   | 조건           | 문구                                                                               |
| --- | -------------- | ---------------------------------------------------------------------------------- |
| 1   | 1위 & T3       | `{ΔD}km 우회하지만 리터당 {가격차}원 저렴해 {NetSaving}원 이득입니다.`             |
| 2   | 1위 & T1       | `경로에서 바로 진입할 수 있으면서 가격도 이 경로에서 {가격순위}번째로 저렴합니다.` |
| 3   | 최저가         | `이 경로에서 가장 저렴합니다. 다만 {ΔD}km 우회가 필요합니다.`                      |
| 4   | 최소 우회      | `경로에서 가장 가깝습니다. 우회 {ΔT}분.`                                           |
| 5   | 필터 조건 매칭 | `{조건}이 있는 곳 중 가장 {모드기준}입니다.`                                       |
| 6   | 그 외          | `가격과 우회 거리의 균형이 좋습니다.`                                              |

- `{가격차}` = `P_ref − P_s`
- `{ΔD}`는 소수 첫째 자리 km, `{ΔT}`는 분 단위 반올림
- **문구 아래에는 항상 지표 3줄을 함께 표시**합니다 (가격 순위 / 우회 / 순이득). 문장만 있으면 근거를 알 수 없고, 숫자만 있으면 읽히지 않습니다

**경고 문구 규칙 — 제거 금지**

| 조건                                   | 문구                                                                    |
| -------------------------------------- | ----------------------------------------------------------------------- |
| 항상                                   | `가격은 실제와 다를 수 있습니다.`                                       |
| **티어가 T3**                          | `+ 먼 거리를 우회하므로 전화 확인을 권합니다.` (전화번호를 반드시 노출) |

> 조건은 **티어 기준**입니다. `ΔD > 3km`가 아닙니다 — `ΔD ≈ F × d_perp`이므로 T2 후보도 `ΔD`가 3km를 넘을 수 있습니다.

**미계산 후보 진입 시**: `detour.precise === false`인 카드로 진입하면, 상세 화면 진입과 동시에 경유 경로를 1회 호출해 실측값으로 교체합니다. 교체 전에는 우회 정보를 `약 …` 표기로 유지합니다.

### 5.6 F10 — 내 주변 주유소

**규칙**

- 정렬: `가격순` / `거리순` 탭 2개
- 카드: `가격 · 거리 · 시설 배지 · 기준시각`
- 탭하면 상세 화면으로 진입. **단 경로가 없으므로 추천 이유·우회 정보·지도의 경유 경로는 표시하지 않는다**
- 내비 연결은 주유소를 목적지로 전달

**이 기능의 위치**

차별점이 없는 기능입니다. 오피넷 앱이 이미 완벽하게 합니다. 그럼에도 넣는 이유는 셋입니다.

1. 경로 탐색은 장거리 이동 때만 쓰이므로 **평소에 열어볼 이유**가 필요하다
2. 경로 기능의 부품(주유소 조회·좌표변환·카드 UI)을 그대로 재사용하므로 추가 비용이 거의 없다
3. 후보 0건일 때의 폴백 화면으로 재활용된다

**→ 여기에 시간을 많이 쓰지 마십시오.** 기능이 커지면 제품의 초점이 흐려집니다.

## 6. Domain Rules

### 6.1 Route (경로)

| 개념            | 정의                                   |
| --------------- | -------------------------------------- |
| 기본 경로 `R₀`  | 출발지 → 목적지 직행. 경유지 없음      |
| `D_base`        | `R₀`의 총 거리 (m, 정수)               |
| `T_base`        | `R₀`의 총 소요시간 (초, 정수)          |
| 폴리라인 `P`    | `R₀`를 구성하는 WGS84 좌표 배열        |
| 경유 경로 `R_s` | 출발지 → 주유소 s → 목적지. 경유지 1개 |

**규칙**

- **복수 경로를 다루지 않는다.** 경로 API가 대안 경로를 반환해도 첫 번째(권장) 경로만 사용합니다. 여러 경로를 비교하는 것은 MVP 범위 밖입니다
- `D_base < MIN_ROUTE_DISTANCE`(20km)이면 안내 후 진행 — 우회 이득이 거의 없는 구간
- 폴리라인 좌표는 **WGS84로 보관**하고, 거리 계산 시에만 미터 단위 투영좌표로 변환합니다
- 경로 API 응답의 `duration`은 실시간 교통 반영 여부가 확인되지 않았습니다. 확인 전까지 "예상 시간"으로만 표기합니다

### 6.2 RefuelPoint (주유소·충전소)

> 오피넷 원본 필드명(`UNI_ID`, `GIS_X_COOR` …)과의 매핑은 [`ARCHITECTURE.md`](ARCHITECTURE.md) §5.1이 소유합니다. **원본 필드명은 `infra/opinet/` 밖으로 새어나가면 안 됩니다** ([`../AGENTS.md`](../AGENTS.md) §7.3). 도메인은 아래 속성만 압니다.

| 속성          | 타입                            | 비고                                     |
| ------------- | ------------------------------- | ---------------------------------------- |
| `id`          | string                          | PK                                       |
| `name`        | string                          |                                          |
| `brand`       | string                          | 표시명 매핑은 §5.2                       |
| `lat` / `lng` | number                          | **WGS84.** 오피넷 KATEC 좌표를 변환한 값 |
| `address`     | string                          | 도로명 우선, 없으면 지번                 |
| `tel`         | string \| null                  | T3 추천 시 필수 노출                     |
| `sigunCd`     | string                          | `P_ref` 시군구 집계 키 (§6.3)            |
| `energyType`  | `OIL` \| `LPG` \| `BOTH`        | LPG 판정                                 |
| `facilities`  | `{ carWash, maintenance, cvs }` | 필터용 — 상세 API 백필로 채워짐          |
| `kpetro`      | boolean                         | 품질인증 — 상세 API 백필로 채워짐        |
| `isSelf`      | boolean \| undefined            | 셀프여부. undefined=미상                 |

**규칙**

- 주유소 마스터는 전부 **`refuel_point`에서 조회**합니다. 가격·상표·주소·셀프여부는 일 1회
  유가 CSV 임포트가, 시설·품질인증·전화는 백필 크론이 채웁니다 ([`ARCHITECTURE.md`](ARCHITECTURE.md) §7.1)
- **영업 여부는 알 수 없습니다.** CSV에 7일 이상 등장하지 않은 곳(`last_seen_on`)은 회랑
  쿼리에서 제외하지만, 그 밖의 폐업은 탐지하지 않습니다

### 6.3 Price (가격)

| 개념             | 정의                                              |
| ---------------- | ------------------------------------------------- |
| `price`          | 리터당 판매가 (원, 정수)                          |
| `pricedOn`       | 가격 기준일자 — 유가 CSV 메타행에서 파싱한 날짜   |
| `P_ref`          | 기준가. "그냥 아무 데나 들렀을 때 냈을 법한 가격" |
| `refPriceSource` | `MEDIAN_T1T2` 또는 `SIGUNGU_AVG`                  |

**가격 갱신 주기**

가격은 **일 1회 유가 CSV 임포트**로 갱신됩니다(새벽). 오피넷 CSV 자체는 카드 단말기
연동분이 하루 6회(1·2·9·12·16시·19시) 반영되지만, 이 서비스가 받는 스냅샷은 하루 한 번입니다.

**실시간이 아닙니다. 항상 몇 시간~하루 지난 값입니다.** 화면에는 기준일자만 표시하고
(`"2026-09-04 기준"`), 별도 "오래된 정보" 경고는 달지 않습니다. 임포트가 실패하면 어제
데이터로 계속 서비스하며 배너로 기준일자를 알립니다 ([`ARCHITECTURE.md`](ARCHITECTURE.md) §5.3.2).

**`P_ref` 산출 규칙 ★**

```
base = T1 ∪ T2   (필터 적용 후)

if count(base) ≥ P_REF_MIN_BASE:        // 2
    P_ref = median(base.price)
    refPriceSource = "MEDIAN_T1T2"
else:
    P_ref = 시군구 가중평균 (아래)
    refPriceSource = "SIGUNGU_AVG"
```

**시군구 가중평균 산출**

1. 필터 적용 후 `pool`의 각 후보에서 `sigunCd`를 모은다
2. 시군구별 후보 수를 가중치로, 해당 시군구의 **선택 연료 평균가**를 가중평균한다
3. 시군구 평균가는 `refuel_point`에서 그때그때 집계한다 (`avg(price_{fuel})`) → **추가 API 호출 0회**
4. 시군구 평균가가 없으면 시도 평균 → 전국 평균 순으로 폴백
5. 전부 없으면 A14 (절감액 표시 생략)

**왜 이렇게 하는가**

- **중앙값을 쓰는 이유:** 평균은 이상치(비정상 저가·고가) 하나에 크게 흔들립니다. 중앙값은 안정적입니다
- **T1+T2를 기준으로 하는 이유:** 사용자가 도구 없이 그냥 운전했다면 눈에 보이는 경로 근처 주유소에 들렀을 것이기 때문입니다. 실제 대안 집합이 기준이어야 "절약"이 정직해집니다
- **T1+T2가 2개 미만일 때 시군구 평균으로 바꾸는 이유:** 후보가 1개면 "중앙값"이 그 한 곳의 가격 자체가 되어 기준이 아니라 우연이 됩니다. 0개면 `pool`(=전부 T3) 중앙값이 되는데, 그러면 "3,252원 이득"이 *경로 주변 대비 절감*이 아니라 *멀리 있는 것들끼리의 상대값*이 됩니다. LPG 저밀도 구간이 정확히 1순위 타깃 시나리오인데, 거기서 핵심 숫자의 의미가 무너집니다

> ⚠️ **화면에 기준을 항상 밝히십시오.** §5.3 ⑤의 문구 규칙을 따릅니다. 기준을 숨긴 절감액은 과장 광고입니다.

### 6.4 탐색 티어 — 제품의 뼈대

주유소를 경로와의 관계로 3등급으로 나눕니다. **결과 화면에서는 하나의 통합 순위로 보여주되, 카드마다 티어 배지를 답니다.**

| 티어   | 배지      | 조건                                                         | 의미                    |
| ------ | --------- | ------------------------------------------------------------ | ----------------------- |
| **T1** | 🟢 경로상 | `d_perp ≤ T1_MAX` (500m)                                     | 경로에서 바로 진입 가능 |
| **T2** | 🔵 근처   | `T1_MAX < d_perp ≤ T2_MAX` (3km)                             | 조금 벗어나면 있음      |
| **T3** | 🟡 우회   | `T2_MAX < d_perp ≤ T3_MAX` (15km) **그리고** `NetSaving > 0` | 돌아가도 이득인 곳      |
| —      | (제외)    | `d_perp > T3_MAX`                                            | **후보에서 제거**       |

**정밀 계산된 상위 후보는 배지를 실측 우회거리로 다시 매깁니다 (STEP 11)**

`d_perp`는 기본 경로까지의 **직선거리**라, 중앙분리대 건너편처럼 붙어 있어도 실제로는 다음 IC까지 갔다 돌아와야 하는 후보가 "경로상"·"근처"로 표시됩니다(§6.5·§11.3 — 실측 우회가 추정의 100~425배인 사례). STEP 10에서 경유 경로를 실측한 후보(최대 `MAX_PRECISE`개)에 한해, 그 실측 우회거리 `ΔD`로 배지를 재판정합니다:

| 배지      | 재판정 조건                                  |
| --------- | -------------------------------------------- |
| 🟢 경로상 | `ΔD ≤ F × T1_MAX` (1km)                      |
| 🔵 근처   | `F × T1_MAX < ΔD ≤ F × T2_MAX` (6km)         |
| 🟡 우회   | `ΔD > F × T2_MAX`                            |

경계값을 `F(DETOUR_ESTIMATE_FACTOR) ×` 기하 임계값으로 잡는 이유: `d_perp`가 `T1_MAX`인 후보의 **추정** 우회거리(`ΔD̂ = F × d_perp`)와 정확히 같은 값이라, 추정 배지와 실측 배지가 경계에서 어긋나지 않습니다.

이 재판정은 **배지 문자열만** 바꿉니다. `P_ref` 계산·T3 게이트·우회 고지 배너(§5.3 ②)는 모두 "경로와의 기하적 관계"가 근거이므로 그대로 `d_perp` 기준 티어(`geoTier`)를 씁니다 — 정밀 계산으로 T3→근처가 된 후보를 두고 "우회해서 N km까지 찾았어요"라고 말하면 배지와 배너가 어긋나기 때문입니다. 추정치만 있는 나머지 후보는 기하 티어를 그대로 표시합니다.

**T3의 조건이 두 개인 이유**

거리만으로는 T3에 넣지 않습니다. "경로에서 12km 떨어짐"은 그 자체로 추천 사유가 될 수 없습니다. 반드시 **"돌아가서 얻는 이득 > 돌아가는 비용"** 이 성립해야 목록에 올라갑니다.

이 조건을 빼면 "왜 이런 먼 데를 추천하지?"가 되고 서비스 신뢰가 무너집니다.

**`T3_MAX`는 상한일 뿐, 실효 도달 거리는 가격 격차가 결정합니다 ★**

게이트 조건을 `d_perp`에 대해 풀면:

```
게이트 : (P_ref − P_s) × Q  >  (F × d_perp / 1000 / E) × P_s
                                          ↑ /1000 을 빠뜨리지 마십시오

d_perp_실효상한 = (P_ref − P_s) × Q × E × 1000 / (F × P_s)     [m]

  F = DETOUR_ESTIMATE_FACTOR (기본 2.0)
```

LPG(`E`=8.5, `Q`=45, `P_s`≈1,100)에서:

| 가격 격차 `P_ref − P_s` | 실효 상한                         |
| ----------------------- | --------------------------------- |
| 40원/L                  | 약 7km                            |
| 60원/L                  | 약 10km                           |
| 108원/L                 | 약 19km → `T3_MAX`(15km)가 바인딩 |

**즉 `T3_MAX`=15km까지 도달하려면 리터당 약 86원 이상의 격차가 필요합니다.** 일상적인 격차(40~60원)에서는 7~10km가 실질 한계입니다. 이건 게이트가 의도대로 동작하는 것이지 버그가 아니지만, **`T3_MAX`를 키운다고 후보가 늘지 않는다**는 뜻이기도 합니다. `T3_MAX`를 조정하기 전에 실제 가격 격차 분포를 먼저 측정하십시오 (§11.3).

**`T3_MAX` 상한은 반드시 적용합니다.** 기본 수집(반경 5km × 8km 간격)에서도 경로 끝단이나 급커브 구간에서 `d_perp > 15km`인 후보가 섞여 들어올 수 있습니다. 티어 분류 단계에서 즉시 제거하십시오.

**T1·T2에는 `NetSaving` 게이트를 적용하지 않습니다.** 경로에 가까운 곳은 손해여도 선택지로서 의미가 있고, 사용자가 "여긴 손해구나"를 확인하는 것 자체가 정보입니다.

### 6.5 Route × RefuelPoint — 이 제품의 핵심

**경로상의 주유소란 무엇인가**
→ `d_perp ≤ 500m`인 주유소 (T1). 여기서 `d_perp`는 주유소에서 기본 경로 폴리라인까지의 최단 직선거리입니다.

**`d_perp` 계산 규칙**

- 점과 폴리라인의 **각 선분**에 대한 최단거리의 최솟값입니다. **폴리라인 꼭짓점까지의 거리가 아닙니다**
- **미터 단위 투영좌표에서** 계산합니다. 위경도(도 단위)로 하면 위도에 따라 왜곡됩니다

**얼마나 떨어진 주유소까지 후보로 보는가**
→ `d_perp ≤ T3_MAX`. 단 `T2_MAX` 초과 구간은 `NetSaving > 0`이어야 합니다. 실질 도달 거리는 §6.4의 공식을 보십시오.

**우회 거리·시간은 어떻게 계산하는가**

| 방식     | 식                                                                               | 언제                                      |
| -------- | -------------------------------------------------------------------------------- | ----------------------------------------- |
| 추정     | `ΔD̂(s) = F × d_perp(s)` [m]<br>`ΔT̂(s) = ΔD̂(s) / 1000 / AVG_SPEED × 3600` [s]     | 모든 후보 (1차)                           |
| **실측** | `ΔD(s) = max(0, R_s.distance − D_base)`, `ΔT(s) = max(0, R_s.duration − T_base)` | 상위 `MAX_PRECISE`개 + 사용자가 탭한 카드 |

> `F` = `DETOUR_ESTIMATE_FACTOR` (기본 2.0). **리터럴 `2`를 코드에 쓰지 마십시오** — 실측 후 보정할 값입니다 (§11.3).
> `ΔT̂` 식에서 `/1000`(m→km)과 `×3600`(h→s)을 빠뜨리면 시간이 3.6배 어긋나 `balanced` 순위가 통째로 틀립니다.

**추정치를 최종 결과로 쓰면 안 되는 이유** — `ΔD ≈ F × d_perp`는 자주 틀립니다.

| 상황                           | 추정  | 실제                 |
| ------------------------------ | ----- | -------------------- |
| 중앙분리대 건너편              | 0.6km | **4km** (유턴 필요)  |
| 고속도로 주행 중 국도변 주유소 | 1.0km | **12km** (IC 진출입) |
| 일방통행 구조                  | 0.4km | 2.5km                |

**정밀 계산이 이 서비스 신뢰도의 전부입니다.** 그래서 실측값만 확정 수치로 표시하고, 미계산 값은 `약 N km ▸`로 구분합니다.

> ⚠️ **추정식의 방향성 문제:** `F × d_perp`는 실제보다 **작게** 나오는 경우가 많습니다(위 표). 그러면 T3 게이트가 통과시키면 안 될 후보를 통과시키고, 정밀 계산 후 회색으로 바뀌는 일이 늘어납니다. `DETOUR_ESTIMATE_FACTOR`는 실측 후 보정 대상입니다 (§11.3).

**`ΔD`만으로는 우회를 표현할 수 없습니다 ★** (Phase 10 실측 — `verify:detour`)

경유지를 넣으면 카카오가 경로를 **재탐색**합니다. 고속도로 대신 국도를 타면 거리는 같거나 짧은데 시간만 늘어납니다. 40.4km 경로에서 추정 상위 40곳을 실측한 결과:

| 지표                       | 값                                                |
| -------------------------- | ------------------------------------------------- |
| `ΔD = 0`                   | **60%** (거리로는 "우회 없음")                    |
| `ΔT` 중앙값                | **7.9분** (p25 4.2 / p75 9.5 / 최대 39.1)         |
| `d_perp` 0~200m 구간 `ΔT`  | 중앙값 **8.2분** (현행 추정 `ΔT̂` 0.2분 — 40배 차) |
| `d_perp` 500~1000m 구간 `ΔT` | 중앙값 **4.8분**                                 |

**`d_perp`가 작을수록 `ΔT`가 오히려 컸습니다.** 경로에 붙어 있는 주유소일수록 간선도로·고속도로 옆이라 진입·복귀가 비싸기 때문입니다. 즉 우회 비용의 지배항은 이탈 거리가 아니라 **진입·복귀 고정비**이고, 그것은 `d_perp`로 예측되지 않습니다.

그래서 **실질 우회 거리**를 정의합니다 — `ΔD`와 `ΔT` 중 나쁜 쪽을 거리 단위로 통일한 값:

```
ΔD_eff(s) = max( ΔD(s),  ΔT(s) / 3600 × AVG_SPEED × 1000 )     [m]
```

`ΔT`를 `AVG_SPEED`로 거리 환산하므로 **새 임계값을 표본 부족 상태로 추정할 필요가 없습니다.** 쓰이는 곳은 `Score_minDistance` 하나입니다 (§8).

> **`ΔD_eff`를 티어 배지 재판정에 쓰지 마십시오.** "경로 117m 옆인데 7분 걸림"인 후보가 🟡우회 배지를 다는데, 우회 고지 배너는 `geoTier`(`d_perp`) 기준이라 켜지지 않아 **배지와 배너가 어긋납니다**(실측 확인: T3 배지 6개 vs 배너 OFF) — §6.4가 금지하는 상태입니다. 우회 시간은 카드 본문의 `+N분 · +N km 우회`가 실측값으로 이미 정직하게 전달하고, 시간이 과도한 후보는 A6 시간 cap이 목록에서 제거합니다.

**음수 클램프가 필요한 이유:** 경유지를 넣으면 경로가 재탐색되어 기본 경로보다 짧거나 빨라지는 경우가 실제로 있습니다. 그대로 두면 "-3분 우회"가 표시됩니다.

**주유 비용과 순절감액**

```
NetSaving(s) = 절감액 − 우회연료비
             = (P_ref − P_s) × Q − (ΔD(s)/1000 / E) × P_s

TotalCost(s) = 주유비 + 우회연료비
             = Q × P_s + (ΔD(s)/1000 / E) × P_s

  P_ref : 기준가 (§6.3)                   [원/L]
  P_s   : 주유소 s의 리터당 가격            [원/L]
  Q     : 주유량 (기본 45)                 [L]
  ΔD    : 우회 추가 거리                   [m]  ← 함수 인자는 m
  E     : 연비 (기본 LPG 8.5)              [km/L]
  결과  : 원 (정수로 반올림)
```

> **단위에 주의하십시오.** `ΔD`는 **미터**로 전달되고 `E`는 **km/L**입니다. `/1000`을 빠뜨리면 우회 연료비가 1,000배가 되어 모든 후보가 탈락합니다. 함수 시그니처 규약은 [`../AGENTS.md`](../AGENTS.md) §7.4를 따르십시오.

> **`NetSaving`에 시간 비용을 넣지 않습니다.** 시간은 `ΔT`로 화면에 별도 표시하고, 시간을 돈으로 볼지는 사용자가 판단합니다. 균형 모드의 정렬에서만 내부적으로 환산합니다 (§8).

**최저가와 최적 주유소를 어떻게 구분하는가**
→ 최저가는 `min(P_s)`, 최적은 현재 기준 모드의 점수가 가장 낮은 후보입니다. 둘은 다를 수 있고, 다를 때 추천 이유 템플릿 #3이 그 차이를 설명합니다.

**여러 경로가 있을 경우** → §6.1대로 기본 경로 하나만 다룹니다. MVP 범위 밖입니다.

## 7. 추천 알고리즘

### 7.1 전체 파이프라인

```
STEP 1  기본 경로 탐색                              [경로 API 1회]
STEP 2  회랑 수집 — 경로 폴리라인 bbox로 refuel_point 조회   [외부 호출 0]
STEP 3  필터 적용 (시설·브랜드·품질인증·셀프여부)
STEP 4  티어 분류 (T1 / T2 / T3후보) + T3_MAX 초과 제거
STEP 7  기준가 P_ref 산출
STEP 8  T3 게이트 — 이득 없는 원거리 후보 제거
STEP 9  1차 스코어링 (추정치)
STEP 10 정밀 계산 — 상위 후보만                     [경로 API 최대 6회]
STEP 11 최종 정렬 + 추천 이유 생성
```

> STEP 5·6은 옛 "확장 수집"(후보가 부족하면 경로에서 더 먼 띠를 추가로 훑던 단계)
> 번호입니다. 회랑 bbox 쿼리가 T3_MAX(15km)까지 한 번에 덮으므로 사라졌고, 다른 STEP
> 번호와 코드 주석을 그대로 두기 위해 번호만 비워 둡니다.

### 7.2 STEP 상세

**STEP 1 — 기본 경로**

```
R₀ = routeAPI(origin, destination)
→ D_base (m), T_base (초), polyline P
```

실패 시 1회 재시도, 그래도 실패하면 전체 중단.

**STEP 2 — 회랑 수집**

```
corridor = bbox(project(P)) 를 T3_MAX 만큼 넓힌 사각형
pool = SELECT * FROM refuel_point
        WHERE lat/lng BETWEEN corridor
          AND price_{fuel} > 0                 // A3 — 미취급 제외
          AND last_seen_on >= today - 7일       // 폐업 추정 제외
```

폴리라인 전체의 bbox를 한 번에 조회하므로 경로 곡률·샘플 간격 같은 개념이 없습니다.
사각형이 실제 회랑보다 넓게 잡히는 만큼은 STEP 4의 `d_perp` 필터가 걸러냅니다.
**`T2_MAX`까지의 후보를 빠짐없이 확보**하므로 `P_ref`(T1+T2 중앙값)가 왜곡되지 않습니다.

**STEP 3 — 필터 적용**

| 필터                      | 적용 방법                                    |
| ------------------------- | ------------------------------------------- |
| 연료 종류                 | STEP 2 쿼리에서 `price_{fuel} > 0`으로 적용 |
| 브랜드                    | `refuel_point.brand_code` 매칭             |
| 시설 (세차·경정비·편의점) | `has_car_wash` 등 — 상세 API 백필로 채워진 값. 미확인(`detail_synced_at IS NULL`) 행은 기본값 `false`라 자동 제외 |
| 품질인증                  | `is_kpetro`                                 |
| 셀프                      | `is_self = true`만. 미상(`NULL`)은 제외     |

전부 `refuel_point` 한 번의 조회 결과에 들어 있어 **추가 호출이 없습니다.**

**STEP 4 — 티어 분류**

```
for each station s in pool:
    d_perp(s) = 점-폴리라인 최단거리(s, P)          // 투영좌표에서

    if d_perp > T3_MAX      → 제거 ★
    elif d_perp ≤ T1_MAX    → T1
    elif d_perp ≤ T2_MAX    → T2
    else                    → T3 후보 (STEP 8에서 게이트)
```

**STEP 5·6** — 옛 확장 판단·수집. §7.1 참고 (제거됨).

**STEP 7 — 기준가 `P_ref`** → §6.3

**STEP 8 — T3 게이트 ★ 핵심 판정**

```
for each s in T3 후보:
    ΔD̂(s) = DETOUR_ESTIMATE_FACTOR × d_perp(s)     // m. 왕복 근사
    if netSaving(s, ΔD̂, P_ref, vehicle) > 0:
        확정 T3
    else:
        제거
```

실효 도달 거리는 §6.4의 공식을 보십시오. **이 게이트가 `T3_MAX`보다 먼저 바인딩되는 경우가 대부분입니다.**

**STEP 9 — 1차 스코어링**

3개 모드 각각의 점수를 **추정 `ΔD̂`, `ΔT̂` 기준**으로 계산합니다 (§8).

**STEP 10 — 정밀 계산**

**대상 선정(STEP 10a)이 STEP 9보다 먼저입니다.** `MAX_PRECISE == MAX_RESULTS`라 여기서 뽑힌 집합이 곧 최종 목록이고, `partial`도 이 집합만 담습니다 — 로딩 중 보던 카드가 통째로 다른 목록으로 바뀌지 않고 **구성원은 그대로 순위·수치만 갱신**됩니다.

```
STEP 10a — 대상 선정
1. 각 모드(balanced·minCost·minDistance)의 추정 순위 상위 ceil(MAX_PRECISE / 3)개를 뽑는다
2. 합집합을 만든다
3. 모드 간 겹침으로 예산이 남으면 현재 모드 점수 순으로 채운다
4. 정렬: 현재 모드 점수 오름차순 → 동점이면 balanced 점수 → 동점이면 id 사전순
5. 상위 MAX_PRECISE(15)개를 자른다
→ 이후 파이프라인은 이 집합만 다룬다

STEP 10b — 실측 (병렬)
for each s in targets:
    R_s = routeAPI(origin, s, destination)      // 경유지 1개
    ΔD(s) = max(0, R_s.distance − D_base)
    ΔT(s) = max(0, R_s.duration − T_base)
    precise = true

실패한 후보(A8): 추정치 유지, precise = false
```

**4단계의 정렬 기준을 반드시 명시적으로 구현하십시오.** Set 순회 순서에 의존하면 같은 입력에 다른 결과가 나옵니다.

**모드별로 대상을 따로 뽑지 않고 합집합을 쓰는 이유:** 사용자가 탭을 전환할 때 API를 다시 부르지 않기 위해서입니다. 3개 모드의 상위권을 미리 다 계산해두면 탭 전환이 즉시 반응합니다.

**STEP 11 — 최종 정렬 + 추천 이유**

```
1. 정밀값이 있으면 정밀값으로, 없으면 추정값으로 NetSaving·점수 재계산
2. 정밀 계산된 후보는 실측 우회거리 ΔD로 티어 배지 재판정 (§6.4 — geoTier는 유지)
3. 우회가 D_base × DETOUR_CAP_RATIO(50%) 또는 T_base × DETOUR_TIME_CAP_RATIO(50%)를
   넘는 후보 제거. D_base < MIN_ROUTE_DISTANCE면 이 비율 대신 절대 시간 상한
   SHORT_ROUTE_DETOUR_TIME_CAP_S(20분)를 적용 (§10.1 A6)
4. 정렬: ① 실측군(precise)이 추정군보다 항상 위 → ② 현재 모드 점수 오름차순
5. 상위 MAX_RESULTS(15)개로 자름
6. 추천 이유 템플릿 적용 (§5.4)
7. expansion.finalRadiusM = 최종 목록에 남은 T3(geoTier) 중 최대 d_perp (없으면 T2_MAX)
```

**4번의 ①이 없으면 정밀 계산이 스스로를 파괴합니다 ★**

실측은 추정보다 우회를 **크게** 잡는 쪽으로만 움직입니다(Phase 10 실측 — 추정 0.1분 → 실측 3~10분). 그래서 실측치와 추정치를 같은 표에서 정렬하면 **실측된 후보가 반드시 집니다.** `MAX_PRECISE`가 6이던 시절 40.4km 노선을 실측한 결과:

| 주유소                | 추정 순위 | 최종 순위 |
| --------------------- | --------- | --------- |
| 진우12주유소          | 1위       | 27위      |
| 후세인주유소          | 2위       | 53위      |
| 경일석유(주) 도영주유소 | 3위       | 17위      |
| ㈜자연에너지 신갈주유소 | 5위       | 22위      |
| 기흥꽃길주유소        | 10위      | 76위      |

**화면에 보이는 15개 중 실측된 것은 0개**였습니다. 정밀 계산이 정확도를 높이는 것이 아니라, 정확한 정보를 화면에서 쫓아내는 필터로 작동한 것입니다. 이 정렬 규칙은 클라이언트의 모드 전환 재정렬(`lib/recompute-candidates.ts`)에도 **똑같이** 들어가야 합니다 — 한쪽만 빠뜨리면 탭을 누르는 순간 다시 뒤집힙니다.

**이미 `partial`로 전송한 후보가 사라지는 문제 — 규칙 우선순위**

| 규칙                             | 이미 보여준 후보에 적용하는가                      |
| -------------------------------- | -------------------------------------------------- |
| 2번 `DETOUR_CAP_RATIO` 초과 제거 | **적용.** 경로가 사실상 달라진 후보는 남기면 안 됨 |
| 4번 `MAX_RESULTS` 절단           | **적용.** 순위 밖으로 밀리는 건 자연스러움         |
| A7 `NetSaving` 음수 전환         | **적용 안 함.** 회색 처리로 남김                   |

클라이언트는 `result` 이벤트를 받으면 목록 전체를 교체합니다. 사라지는 항목이 있을 수 있으며, 이는 정상 동작입니다. **다만 1위 카드가 사라지면 짧은 안내를 띄우십시오** — `정밀 계산 결과 순위가 바뀌었습니다`.

### 7.3 왜 2단계로 나누는가 (추정 → 정밀)

정확한 우회 거리를 알려면 후보마다 경유 경로 API를 호출해야 합니다. 후보가 40개면 40번입니다. 그래서 **싼 계산으로 걸러내고, 비싼 계산은 소수에게만** 씁니다.

| 방식                                    | 검색당 경로 API          |
| --------------------------------------- | ------------------------ |
| 전 후보 정밀 계산                       | 150+                     |
| **화면에 올릴 `MAX_PRECISE`개만 정밀 (채택)** | **16** (기본 1 + 정밀 15) |

**약 10배 차이입니다.** 실제 쿼터 대비 환산은 [`ARCHITECTURE.md`](ARCHITECTURE.md) §5.3.

**`MAX_PRECISE`는 `MAX_RESULTS`와 같아야 합니다 ★** — 화면에 올리는 후보는 전부 실측합니다. 예산을 아끼려고 이 수를 줄이면 "싼 계산으로 걸러내고 비싼 계산은 소수에게"가 아니라 **"비싼 계산을 한 후보만 목록에서 탈락시키는"** 구조가 됩니다 (§7.2 STEP 11). 줄여야 한다면 `MAX_RESULTS`를 함께 줄이십시오.

## 8. 기준 모드 3종

세 모드 모두 **같은 계열의 목적함수**이고, 항이 하나씩 늘어나는 구조입니다. 전부 **최소화** 문제입니다.

### 최단거리

```
Score_minDistance(s) = ΔD_eff(s) = max( ΔD(s), ΔT(s) / 3600 × AVG_SPEED × 1000 )   [m]
```

우회만 본다. 가격 무시. _"돌아가기 싫다"_

**`ΔD`가 아니라 실질 우회 거리(§6.5)를 쓰는 이유:** 실측 후보의 **60%가 `ΔD = 0`** 입니다(경유지를 넣으면 경로가 재탐색되어 거리는 그대로인데 시간만 늘어남). `ΔD`만 보면 그 60%가 전부 0점 동점이 되어 "최단거리" 정렬 자체가 무의미해집니다.

### 최소비용

```
Score_minCost(s) = TotalCost(s)
                 = Q × P_s  +  (ΔD(s)/1000 / E) × P_s      [원]
                   └주유비┘    └──── 우회 연료비 ────┘
```

주유비와 우회로 더 태우는 기름값의 합. 시간 무시. _"돈만 아끼면 된다"_

### 균형 (기본값)

```
Score_balanced(s) = TotalCost(s) + (ΔT(s)/60) × V_TIME     [원]
                                   └── 시간 비용 ──┘
```

시간을 돈으로 환산해서 더한다. `V_TIME` 기본 200원/분 (시급 12,000원 기준).

> **단위:** `ΔD`는 m, `ΔT`는 초로 전달됩니다. `E`가 km/L이고 `V_TIME`이 원/분이므로 함수 내부에서 각각 `/1000`, `/60` 변환이 필요합니다. [`../AGENTS.md`](../AGENTS.md) §7.4.

### 설계 메모

- **전부 원(₩) 단위라 자연스럽게 합쳐집니다.** 정규화나 임의 가중치가 필요 없습니다. 이 설계의 가장 큰 장점입니다
  - 예외: `minDistance`만 m 단위입니다. 다른 두 모드와 점수를 비교하지 마십시오. 모드 내 정렬에만 씁니다
- **정렬의 1차 키는 모드 점수가 아니라 `detour.precise`입니다** (§7.2 STEP 11) — 실측군이 추정군보다 항상 위. 세 모드 모두 같습니다
- **가중치 슬라이더를 두지 않습니다.** "가격 0.7 / 시간 0.3"이 무슨 뜻인지 사용자는 모릅니다. **탭 3개로 사용자가 의도를 표현하게** 합니다
- 화면에 표시하는 `NetSaving`은 모드와 무관하게 **항상 시간 미포함 금액**입니다. 우회 시간은 별도로 항상 표시됩니다. 판단은 사용자 몫입니다

가장 빠른 길을 찾고 있어요       ●○○○     progress: ROUTE
근처 주유소를 살펴보고 있어요     ●●○○     progress: COLLECT
조금 더 넓게 찾아보고 있어요      ●●●○     progress: EXPAND   ← 최종 후보에 T3가 있을 때만
곧 결과를 보여드릴게요           ●●●●     progress: PRECISE
```

> **`EXPAND` 단계는 T3 후보가 최종 목록에 남았을 때만 방출됩니다** (STEP 8 직후). 실제 반경이
> 있으면 `반경 {N}km까지 넓혀서 찾아보고 있어요`로 구체화합니다. 이 숫자("어디까지 살폈나",
> `T3_MAX`)와 결과 배너 숫자("어디서 찾았나", 채택된 T3의 최대 `d_perp`)는 서로 다릅니다 —
> [`ARCHITECTURE.md`](ARCHITECTURE.md) §6.2.

> 이 문구들은 **가짜 애니메이션이 아닙니다.** 서버가 실제 단계를 스트리밍으로 알려줍니다.

> **JSON 폴백이 걸린 경우에만 예외입니다.** 진행 상태를 알 수 없으므로 `EXPAND` 문구는
> 절대 보여주지 않고, 나머지 문구만 시간 기반으로 순환시킵니다 — 최종 후보에 T3가 있는지
> 모르는 상태에서 "넓게 찾는 중"을 띄우면 이 제품이 가장 경계하는 "근거 없는 표시"가 됩니다.

## 11. 성공 지표와 로깅

### 11.1 지표 3개

| 지표                              | 왜 이것인가                                                      |
| --------------------------------- | ---------------------------------------------------------------- |
| **T3 발동률**                     | T1·T2로 충분해서 T3가 거의 안 뜬다면, 차별 기능이 사실상 없는 것 |
| **T3 발동 검색의 내비 연결률**    | 우리가 찾아준 "우회할 가치 있는 곳"을 사용자가 실제로 채택했는가 |
| **T1·T2만 뜬 검색의 내비 연결률** | 위 지표의 비교군. 두 값이 같으면 T3 탐색은 헛수고였다는 뜻       |

### 11.2 로깅 정책

이 지표를 측정하려면 서버 이벤트 기록이 필요합니다. **개인 식별 가능 정보는 저장하지 않습니다.**

| 저장한다                                       | 저장하지 않는다               |
| ---------------------------------------------- | ----------------------------- |
| 익명 검색 ID, 시각                             | 사용자 ID, 세션 쿠키          |
| 연료, 적용 필터                                | IP 주소, User-Agent 원문      |
| 기본 경로 거리·시간                            | **정확한 출발지·목적지 좌표** |
| 출발·목적 **격자 스냅 좌표** (2km 격자)        | 장소 이름                     |
| 티어별 후보 수, 최종 후보 T3 포함 여부·최대 거리 |                             |
| `P_ref`와 그 출처                              |                               |
| 딥링크 클릭: 앱·순위·티어·순절감액             |                               |

원본 기획의 _"서버에 사용자 데이터를 저장하지 않는다"_ 는 **"개인 식별 가능 데이터를 저장하지 않는다"** 로 해석합니다. 익명 집계 이벤트는 저장합니다. 이 지표 없이는 T3 탐색이 가치가 있는지 검증할 수단이 없습니다.

스키마는 [`ARCHITECTURE.md`](ARCHITECTURE.md) §7.3.

### 11.3 파라미터 확정 전 실측이 필요한 값

**미해결 검증 항목의 정본 목록은 [`ARCHITECTURE.md`](ARCHITECTURE.md) §12입니다.** 여기서는 그중 **제품 판단이 걸린 것**만 봅니다.

| 측정 대상                    | 스크립트         | 판단 기준                                                                                                            |
| ---------------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **T3 발동률**                | `verify:t3-rate` | 노선 3개 × 연료 3종 × 필터 유무로 최종 후보에 T3가 남는 비율. **LPG에서 20% 미만이면 차별 기능이 거의 안 뜸 → 기획 재검토** |
| **T3 게이트 통과율**         | `verify:t3-rate` | 게이트 진입 후보 중 `NetSaving > 0`인 비율. **10% 미만이면 T3 탐색이 헛수고**                                          |
| **가격 격차 분포**           | `verify:t3-rate` | 노선별 `(P_ref − min(price)) × 45L`. 평균 3,000원 미만이면 우회할 이유 자체가 약함. §6.4의 실효 상한도 여기서 결정됨 |
| **`ΔD̂` vs 실측 `ΔD` 오차**   | `verify:uturn`   | `DETOUR_ESTIMATE_FACTOR`(현재 2.0) 보정용. 과소추정이 심하면 계수를 올려야 함                                        |
| **T3 후보의 우회 시간 분포** | `verify:t3-rate` | 평균 +40분 이상이면 `T3_MAX`를 줄여야 함                                                                             |
| **실측 `ΔT` 분포 · `ΔD=0` 비율** | `verify:detour` | `DETOUR_TIME_CAP_RATIO` 확정용. **현재 근거는 노선 1개(40샘플)뿐** — 여러 노선·연료로 재측정해야 합니다 ([`ARCHITECTURE.md`](ARCHITECTURE.md) §12 ⑭) |

**T3 발동률과 게이트 통과율이 가장 중요합니다.** 둘 중 하나라도 낮으면 T3 탐색을 뺀 서비스가 되고, 그건 기존 서비스와 다를 게 없습니다.

> `verify:coverage`(샘플 간격에서 T2 누락률)는 후보 수집이 회랑 bbox 쿼리로 바뀌어
> 의미가 없어졌습니다 — bbox가 `T2_MAX`를 포함하므로 T2 누락이 구조적으로 0입니다.
